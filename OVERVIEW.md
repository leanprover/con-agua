# con-agua: an overview

> **This document was written by an AI agent** (Claude, working with the
> maintainer); `README.md` is the human-written entry point. It describes the
> checker and its proof as they are.

con-agua is a Lean kernel checker in x64 machine code. It is a close clone of
[con-ron](https://github.com/leanprover/con-ron)'s checker, written in a small
first-order language **L**, compiled to x64 by a **verified compiler**, and
shipped as one committed assembler file,
[`checker.s`](checker.s). A Lean theorem relates that file, as an x64
program in [Kraken](https://github.com/sgraf812/kraken)'s semantics, to
con-ron's Lean twin and through it to
[con-leche](https://github.com/leanprover/con-leche)'s verified kernel: if the
machine reports *accept*, con-leche's pure checker accepts the same bytes, so the
accepted environment has a model and declares no theorem of type `False`.

The point is diversity, as for con-ron. con-leche's proof is about Lean code
that runs on Lean's compiler and runtime; con-ron's is about Rust that runs on
`rustc`. con-agua's checker runs on no compiler and no runtime that the proof
does not cover: the code the CPU executes is the code the theorem is about, up
to the assembler, the loader and a C harness of about two hundred lines.

The reader is assumed to know con-leche and con-ron. Three names recur:

* **con-leche**, its pure checker `checkDeclsPure`, whose soundness theorems are
  the ones inherited here.
* **the twin**: con-ron's checker written in Lean
  ([`vendor/con-ron/ConRon/Arena/`](vendor/con-ron/ConRon/Arena/)), which works
  on con-ron's data representation (handles, per-tier stores, hash-consing) and
  mirrors con-ron's Rust function for function. con-ron proves that the twin
  refines con-leche (its Theorem 1) and that its Rust refines the twin (its
  Theorem 2). con-agua uses Theorem 1 and replaces Theorem 2: here L refines
  the twin.
* **L**, the language the checker is written in
  ([`ConAgua/L/`](ConAgua/L/)), and **the checker** `checkerProg`, an L program
  of about 1800 functions ([`ConAgua/Checker/Prog.lean`](ConAgua/Checker/Prog.lean)).

con-ron and con-leche are vendored under [`vendor/`](vendor/) at the revisions
in [`vendor/UPSTREAM`](https://github.com/leanprover/con-agua/blob/master/vendor/UPSTREAM#L3-L4);
only their Lean parts that do not need Aeneas are built.

## 1. Building and usage

### 1.1 Building

Run `make`. It needs a C compiler with C23 `#embed` (GCC ≥ 15 or Clang ≥ 19)
and an x86-64 Linux assembler, nothing else; `make check` is a smoke test. The
binary is built from four committed files at the repository root:
[`main.c`](main.c), the C harness, which reads the input, calls the checker
once and prints the verdict; [`checker.s`](checker.s), the checker, generated by
the verified compiler; [`pins.bin`](pins.bin), the pin data
(con-leche's `Nat`-operation pin variants and the checker's startup data: the
names it pins and the structured constants it reads),
embedded into the binary; and [`reasons.h`](reasons.h), the messages of the
abort reasons, generated from [`scripts/reasons.tsv`](scripts/reasons.tsv).

### 1.2 Running it

```
./checker [--jobs=N] FILE.ndjson
./checker --compare [--] CHALLENGE.ndjson SOLUTION.ndjson
```

`FILE.ndjson` is a `lean4export` export. `--jobs=N` with `N > 1` checks the
declaration bodies on `N` threads (§9.3); without it the check is sequential.
The checker prints one verdict line and exits with status 0 only on accept
([the usage text](https://github.com/leanprover/con-agua/blob/master/main.c#L1-L44),
[`print_verdict`](https://github.com/leanprover/con-agua/blob/master/main.c#L84-L96)):

| exit | line | meaning |
|---:|---|---|
| 0 | `accept` | every declaration checked; the only accept |
| 1 | `rejected: M` | the checker stopped where the twin fails with `invalid` (message `M`, the twin's own) |
| 2 | `declined: M` | the checker stopped where the twin fails with `notImplemented` |
| 3 | `error: M` | any other stop: a capacity of the checker, a check the twin does not make, a twin error the checker does not label; claims nothing |
| 3 | `exhausted` | a resource ran out: the step budget, the stack or the memory region |
| 3 | `ok R` | the run stopped early: `ok 1` is a line the parser did not accept |
| 3 | none | a failure of the harness itself (bad usage, a file it cannot read, no memory), with a message on stderr |
| signal | none | a crash, for instance a page the kernel cannot supply |

`--compare` checks the export `CHALLENGE.ndjson` with its holes justified by
`SOLUTION.ndjson`, as con-ron's and con-leche's `--compare` do: the solution is
checked as a `FILE.ndjson` is, then the challenge, where every axiom other than
the built-in ones, and every definition, theorem or opaque constant whose value
uses `sorryAx` (read as the axiom of its statement), must be justified by a
constant of the solution with the same name and the same statement up to a
renaming of level parameters, whose type reads only constants that are the
same in both files. Both files are read into one store. The verdict line and
the exit status are as above; two files that are not two different paths are a
usage error (exit 3, no verdict line). The compared run is sequential: `--jobs`
does not combine with it
([docs/deviations.md](docs/deviations.md), D51).

Every way the checker says no is an L `abort` with a code: the low two bits
are the class (`1` reject, `2` decline, `0` other), the rest a reason, whose
message the harness prints. The code comes back in `rax`
([`OutcomeRel`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Main.lean#L30-L33)). A reject or decline
site is labelled with the twin's message where the twin fails in the same way at
the same point (`fail R`). The labels are proved: an exit 1 or 2 means the
twin's pipeline fails on the input with `invalid` resp. `notImplemented`
(§2.1). The messages are not part of the theorem; on the test corpus they are
con-ron's own
([deviation D16](https://github.com/leanprover/con-agua/blob/master/docs/deviations.md#L48)).
Internally, accept is the return word `0x414343455054`, chosen so that no
status word or unset register reads as accept
([`ACCEPT`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/Statement.lean#L99-L101)).

## 2. What is proven, what is trusted

### 2.1 The final theorem

[`checkerFile_accepts`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/EndToEnd.lean#L96-L104):

```lean
theorem checkerFile_accepts [Host]
    (k0 : Nat) (hcode : Code checkerFile k0)
    (b pb : ByteArray) (h64 : System.Platform.numBits = 64)
    (dm : MachineData) (ra : Word) (hc : AbiCall b pb dm ra) :
    Ev (fun st => st.pc = Int64.ofBitVec ra.toBitVec ∧
        (st.data.regs.rdx = 0 → st.data.regs.rax = ACCEPT → TwinAccepts [b]) ∧
        (st.data.regs.rdx = 2 → st.data.regs.rax &&& 3 ≠ 0 →
          TwinVerdict [b] (st.data.regs.rax &&& 3)))
      dm (label abiStartL)
```

In words: take any Kraken host program (`[Host]`) that contains the code of
`checker.s` at some position (`hcode`; `checkerFile` is the file as the
trusted parser reads it, §8.4). Call its entry point `ca_start` from a machine
state `dm` in the way the harness does (`AbiCall`: the input bytes `b`, the pin
data `pb`, a zero region, a return address `ra`). `ca_start` is the sequential
driver (§9.2): it runs entry 1 (the stages and the stream index) and then
entry 2 (every record's job) on the same region, each one L run of `check`.
Then **every run returns to `ra`**; if it returns `rdx = 0` and `rax = ACCEPT`, the twin's pipeline
accepts `b`; and if it returns `rdx = 2` with a code whose class `rax &&& 3` is
`1` (reject) or `2` (decline), the twin's pipeline fails on `b` with an error of
that class. Every other outcome (`rdx = 1`, class `0`, `ok R`) claims nothing. `Ev` is Kraken's "every run from here reaches the postcondition"
([`Ev`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Step.lean#L25-L30)):
an inductive, so the run also terminates in Kraken's semantics, whatever the
input. The theorem takes no set-theory model: a record's job is checked at the
stream index's view of its position, and con-ron's Theorem 1 obtains the fold
invariant there from con-leche's model-free fact that the pure fold keeps the
environment well formed
([`foldlM_checkDecl_envWF`](https://github.com/leanprover/con-agua/blob/master/vendor/con-leche/ConLeche/Semantics/DeclWF.lean#L306-L308)).

[`TwinAccepts`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/Twin.lean#L77-L87)
is the stages con-ron's binary runs, from the twin's start state: intern the
reserved names, parse the built-in prelude, parse the input, prepare the
records, intern the pins, then the check phase, at some pin list. The pins
are interned with the run's maximum `Nat` size, which here is always the
default, 134 217 728 bytes
([`maxNatSizeDefault`](https://github.com/leanprover/con-agua/blob/master/vendor/con-ron/ConRon/Arena/CoreState.lean#L147-L149));
the checker has no `--max-nat-size` flag, which con-ron's binary has. The check
phase is
[`SeqAccepts`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/Twin.lean#L59-L64):
the stream index (`buildIndex`, which reads every record off once, with no
inference), then every record's job, in order, on one worker; a job checks its
record at the index's view of the record's position.
[`TwinVerdict [b] c`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/TwinVerdict.lean#L63-L64)
is the same pipeline
([`twinRun`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/TwinVerdict.lean#L52-L59)), at some pin
list, failing with an error of class `c` (`invalid` is `1`, con-ron's exit
code 1; `notImplemented` is `2`, exit code 2), in the monad or as a reported
failure of a line or a record. There is no converse: a run that the twin
rejects may still end in `error` or `exhausted` here.

Two corollaries put this in con-leche's terms
([`checkerFile_model_exists`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/EndToEnd.lean#L116-L128),
[`checkerFile_no_False`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/EndToEnd.lean#L142-L149)):
on accept, con-leche's own parser reads `b`, con-leche's pure fold accepts the
parsed records (prepared with some prelude, at some pin list), and the accepted
environment has a model in every `ConLeche.SetTheory V`; and a file in
`jsonWithTheoremFalse`'s shape is never accepted. Their glue is con-ron's
capstone, restated on the vendored Theorem 1
([`twinAccepts_pure`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/Twin.lean#L89-L109)).
A fourth variant,
[`checkerFile_accepts_regs`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/EndToEnd.lean#L77-L85),
adds that the caller's callee-saved registers (System V: `rsp`, `rbp`, `rbx`,
`r12` to `r15`) are intact on return, on every path
([`RegsRestored`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/Statement.lean#L130-L137)).
The trampoline saves and restores them; nothing is assumed about the registers
the compiled code uses (§8.1).

**Axioms.** All four, and the five threaded theorems (§9.3), depend on `propext`, `Classical.choice` and `Quot.sound`
only, pinned by `#guard_msgs`
([here](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/EndToEnd.lean#L206-L223)),
and so do the links of the chain
([`ConAgua/Audit/Final.lean`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Audit/Final.lean#L20-L37)).
No `sorry`, no `native_decide`, no axiom of our own. The model and
no-`False` corollaries (and their threaded forms) are relative to set theory
as con-leche's model theorem is: they take `[ConLeche.SetTheory V]` (a model
of ZF⁻ with an ω-chain of Grothendieck universes), which cannot be
instantiated inside Lean, so they give their conclusion only given such a
model. The accept and verdict theorems take no such model.

`TwinAccepts` is not trivially true: given a set-theory model, some input is
not accepted
([`twinAccepts_not_trivial`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Audit/Final.lean#L47-L50)).

### 2.2 What the theorem's hypotheses mean

* **`AbiCall`**
  ([def](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/Abi.lean#L26-L52)):
  the System V arguments `ca_start(in, in_len, pins, pins_len, base,
  base_len)`; the buffers hold `b` and `pb`; the region `[base, base +
  base_len)` is zero, mapped, apart from both buffers and from 32 bytes of
  machine stack around `rsp`; the return address is on the stack. This is the
  harness's whole contract. The layout inside the region (the descriptor table,
  the L stack, every array) is *not* assumed: the entry stubs build it and the
  proof checks it (§8.3). A region that is too small makes the driver return
  `rdx = 1`. `AbiCall` does not bound the buffer sizes: a length register is a
  64-bit word, and the setup stub returns `rdx = 1` when the top bit of
  `in_len` or `pins_len` is set, so a run that gets past it has both buffers
  below `2^63` bytes, which the refinements assume (§8.3).
* **`hcode`, `[Host]`**: the program Kraken runs contains the file's code. The
  `Host` class fixes where the assembler and linker put each directive.
* **`h64`: a 64-bit platform.** `System.Platform.numBits` is an opaque
  constant in Lean's logic (32 or 64, fixed by the platform the code runs on),
  so it cannot be proved; the twin's parser indexes the input with `USize`,
  whose width it sets, and the refinements of the frontend need it to be 64
  bits, the width of the machine words.
* **The pin data `pb` is arbitrary.** The checker decodes it at run time, and
  `TwinAccepts` holds at the pin list it decoded; con-leche's theorems hold at
  every pin list. The prelude is not an assumption either: con-leche's
  `preparePrelude` puts its records into the checked stream
  ([the module doc](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/Twin.lean#L47-L49)).
* **Capacities and fuel are not assumptions.** The stub gives every word
  array `2^32` words and each entry's run `2^62 - 1` units of fuel; the refinement holds
  at every capacity and every fuel below `2^62`
  ([`InputsOK`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Pipeline.lean#L74-L77), what the stages assume),
  and the checker aborts on a size it cannot work with.

### 2.3 The trusted base

| trusted | what it is | what stands in for it |
|---|---|---|
| **Kraken's x64 semantics** | the meaning of each instruction the compiler emits | Kraken's test suite and differential instruction fuzzer, which compare it with native execution; its scope is sequential code, without virtual memory or access permissions ([Kraken](https://github.com/sgraf812/kraken)) |
| **the assembler, linker and loader** | that the bytes executed are the instructions of `checker.s` at the addresses `Host` describes | [`scripts/check-asm.sh`](https://github.com/leanprover/con-agua/blob/master/scripts/check-asm.sh#L1-L12) assembles and disassembles the file and compares every instruction with what Kraken's printer meant; branch and call targets are not compared, so label resolution is trusted |
| **the assembler-file parser** | `include_asm`, which turns `checker.s` into the term `checkerFile` | it prints the code back and compares it with the file; Kraken's independent parser must read the file the same way (§8.4) |
| **the C harness** | [`main.c`](main.c): reads the input, maps the region, calls `ca_start` as `AbiCall` says with the embedded pin data, reads `rdx` and `rax` | review; about two hundred lines with no checker logic. That its callee-saved registers survive each call is proved (`RegsRestored`, §2.1), for the threaded entries too (§9.3) |
| **reading the file** | that the bytes `b` are the file's | the theorem is about whatever bytes the buffer holds; [`read_input`](https://github.com/leanprover/con-agua/blob/master/main.c#L149-L167) maps a regular file read-only and reads anything else (a pipe) until end of file; a file that another process changes during the run is outside the theorem |
| **the operating system** | `mmap` of a `MAP_NORESERVE` region of about 6 TiB of address space, whose pages become real when touched | a page the kernel cannot supply kills the process (a signal or the OOM killer), which is never an accept |
| **Lean's kernel, and con-leche's own assumptions** | as for con-leche and con-ron | their documentation |

**The threaded mode** (`--jobs=N`, §9.3) has its own theorem, and its harness
assumptions are the fields of
[`ThreadsRun`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/ThreadsFinal.lean#L146-L181)
([listed in words](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/ThreadsFinal.lean#L32-L55)):

* entry 1 is called as `AbiCall` says, and the harness regains control at each
  call's return address in a state the machine is guaranteed to reach there
  (`FirstReturn`);
* the frozen buffer is the first `len` words of `OUT` at entry 1's return and
  stays in place: every call is passed its address and sees the same words
  before and after (read-only, by `mprotect`);
* each thread's region is its own, apart from the other threads' regions, the
  buffer and every thread's stack window (pthreads); it is zero at the thread's
  first call and holds what the previous call left at each later one;
* every claimed job index is below `k` (entry 1 returned `2^63 + k`, `k` the
  number of records), and every index below `k` is claimed by some thread (the
  atomic counter);
* each thread's claims increase: a later call of a thread claims a larger index
  (one counter, incremented by `__atomic_fetch_add`). con-ron's pool needs each
  worker's jobs in increasing order, since a worker's state carries across its
  jobs;
* entry 1 returned `rdx = 0`, `rax ≥ 2^63`, and every call `rdx = 0`, `rax =
  ACCEPT`.

The threaded verdict theorem (`checkerFile_threads_verdict`) has its own set,
the cases of
[`ThreadsFail`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/ThreadsVerdict.lean#L76-L124)
([listed in words](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/ThreadsVerdict.lean#L41-L65)):
either entry 1 is called as `AbiCall` says and returns (`FirstReturn`) with
`rdx = 2`, and the code reported is its `rax`; or, for one thread and one of
its calls `i`, the facts above hold for that thread's calls up to `i` (entry 1
returned `rdx = 0` and `2^63 + k`, the buffer in place, the thread's own region,
zero at its first call and carried from call to call, every claimed index below
`k`, the calls before `i` claiming smaller indices than `i`), its calls before
`i` returned `ACCEPT`, call `i` returned `rdx = 2`, the code reported is that
call's `rax`, and every job index below call `i`'s was claimed by a call of some
thread that returned `ACCEPT`, those threads' calls being as `ThreadsRun` has
them (`ThreadsAcc`). The last fact is what the harness's report gives: the
counter hands out `0, 1, 2, …` in order, a thread finishes the call it holds
and records only its first failure, and after joining every thread the harness
reports the failure with the smallest index, so every lower index was claimed,
run and accepted. Nothing is assumed about the claiming covering every index.

Not trusted: the compiler and its Lean execution (the kernel checks the
compiled code, §8.4), the printer that wrote the file, the entry stubs, the
pin-data generator, the layout of memory, the capacities.

### 2.4 What the theorem does not cover

* **Completeness.** The theorem says what an accept, a reject and a decline
  mean; it says nothing about a run that ends in `error`, `exhausted` or
  `ok R`, and there is no converse: the checker may end in `error` or decline
  where con-ron accepts or rejects. It never accepts where con-leche rejects.
  A reject or decline is the twin's (con-ron's arena checker); con-ron proves
  no error-kind version of its Theorem 1, so this is not a statement about
  con-leche's reject. The messages printed with a reject or decline are not
  part of the theorem. The
  known places where L declines inputs the twin would accept are the
  completeness rows of [`docs/deviations.md`](docs/deviations.md) (§10.2).
  Exhaustion of the L stack (1 GiB) or the fuel is `rdx = 1`, never accept
  ([the compiler theorem](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Main.lean#L29-L33)).
* **The threaded mode's harness** is assumed, not proved (§2.3): the
  theorem for `--jobs=N` takes the threads' behaviour as hypotheses.
* **What con-leche does not cover**: the checker checks `--verified` mode
  only; con-leche's assumptions carry over unchanged.

### 2.5 Building the proof

One Lean toolchain,
[`nightly-2026-10-20`](https://github.com/leanprover/con-agua/blob/master/lean-toolchain#L1)
(from `elan`), for everything: the proofs, Kraken (a Lake dependency, pinned by
[rev](https://github.com/leanprover/con-agua/blob/master/lakefile.toml#L9-L12)),
and the vendored con-ron and con-leche.

```
scripts/lake build
```

builds the default targets: the library `ConAgua` (L, the compiler, the
checker, all proofs), `ConAguaAsm` (which reads `checker.s`, §8.4), and the
vendored `ConLeche`, `ConRonArena` and `ConRonBridge`. `scripts/lake` is a
wrapper around `lake` that shares one artifact cache between git worktrees;
outside the project's worktree setup plain `lake build` does the same work. The
final theorem is built with everything else; its axioms are pinned by
`#guard_msgs` (§2.1), so a successful build is the check.

Regenerating the committed `checker.s` and `pins.bin` is described in §8.5.

## 3. Performance

con-agua is compared with con-ron, its release binary at the vendored
revision (on one thread with `--jobs=1`), on Lean's `Init` (exported by
`lean4export` at Lean 4.35.0, 346 MB) and on other large inputs. con-agua
executes more instructions than con-ron, but its code is instruction-bound
(more instructions per cycle), so its extra instructions cost less time than
their number suggests. On a busy machine the gap widens, because a busy
sibling hyperthread takes the issue slots con-agua depends on; wall times are
therefore measured on a quiet machine. The tables are produced by
[scripts/perf-overview.py](scripts/perf-overview.py) (`--write`), which builds
the checker with `make`, runs both checkers in interleaved rounds and
replaces them in this section.

## 4. Architecture

```
checker.s          ⊑  checkerProgI (L)       the verified compiler, compile_correct, against Kraken's x64 semantics
checkerProgI       ⊑  checkerProg            the inliner, inlineProg_run (one more unit of fuel)
checkerProg        ⊑  the twin's pipeline    drv_twinAccepts: per-function refinements, composed along both entries
the twin           ⊑  con-leche's pure fold  con-ron's Theorem 1 (vendored)
con-leche accepts  ⇒  a model, no False      con-leche
```

### 4.1 L

L is a small first-order language made for this checker
([syntax](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Syntax.lean#L5-L16)):
64-bit words, numbered locals, a fixed set of byte and word arrays named by
static indices (a word array of a tiered table also by its tier), global word variables, loops, calls, and structured control
flow. No pointers, no closures, no allocation: a growable vector is a
fixed-capacity array and a length word. Its meaning is a Lean function into
`StateT St (Except Err)` with fuel (§5.2), which is both executable and what
`vcgen` steps through. §5 has the details.

### 4.2 The verified compiler

`compileProg` translates an L program to Kraken x64 in one pass, without
optimisation beyond a few local ones (§8.1) and a bounds-check analysis (§8.7). Before it, one L → L pass inlines
small leaf functions into their callers (§8.6); what the compiler compiles is
`checkerProgI`, which refines `checkerProg`.
[`compile_correct`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Main.lean#L778-L802)
is a forward simulation against Kraken's semantics: from `ca_enter`, with L's
memory `m` laid out as the layout `G` describes (`MemRel`), 32 mapped bytes
past the table (where the trampoline saves registers) and `N` units of fuel,
every run returns to the caller with the callee-saved registers restored and
either reports `rdx = 1` (exhausted) or reports exactly what `L.run p N entry
args m` says
([`OutcomeRel`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Main.lean#L29-L33)):
the results and the final memory, or `rdx = 2` for an error, with the error's
code in `rax` (an abort's own code, `0` for any other error). It is proved once,
for every well-formed program. It also allows a table of hand-written function
bodies in place of compiled ones (`compileProgX`), each proved against the same
per-function contract as the compiled code (`AsmOk`). The checker has two, the
bignum rows `mul_row` (multiply-accumulate,
[`mulRowAsm_sim`](ConAgua/AsmEsc/MulRowAsm.lean)) and `sub_row` (subtract,
[`subRowAsm_sim`](ConAgua/AsmEsc/SubRowAsm.lean)), listed in
[`Checker/AsmX.lean`](ConAgua/Checker/AsmX.lean).

### 4.3 Kraken

[Kraken](https://github.com/sgraf812/kraken) is a Lean model of x64 for
sequential code: registers, flags, memory as a partial map, assembler labels.
The judgment is `Eventually (step1 Host.exe) Q`, "every run reaches `Q`"; a
load or store outside the mapped memory has no successor state, so a proof of
`Ev` also shows that the code never touches memory it was not given.

### 4.4 L against the twin

The checker mirrors the twin function for function. Each L function has a
twin function it stands for (a citation line names it, §10.1), and a
refinement theorem: if the L function returns, the twin function succeeds on a
related state with a related result
([`RefAM`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/IndIface.lean#L358-L369),
the shape most refinements have). The relations say how L's arrays represent
the twin's state (§6, §7). The refinements compose along entry 1's stages
([the stage specs](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Pipeline.lean#L97-L130)) and the stream index's build into
[`checkA_run`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/CheckARun.lean#L163-L169),
and with entry 2's jobs into
[`drv_twinAccepts`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/ParDriverTwin.lean#L101-L111):
an entry-1 run of `check` from the loaded memory followed by an entry-2 run on
the memory it left, the second returning `ACCEPT`, comes from an accepting twin
pipeline on the same bytes.

These are **partial-correctness** statements: an L run that runs out of fuel
or returns anything else claims nothing. That is what makes the approach
practical: L may abort wherever it likes (a full table, an unusual input), and
only the accept path has to agree with the twin. An abort of class `1` or `2`
is the one exception: a failing call with such a class claims the twin
function's failure with the same class from the related state
([`ErrClaim`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/Verdict.lean#L54-L55)).
For these functions one refinement covers both outcomes
([`RefE`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/Verdict.lean#L245-L249)):
it is proved from a word model that keeps the errors (`l_model … unified`:
`Except` instead of `Option`) by one case chain, where a callee's failure passes
through the twin's `bind` and at a reject or decline site the L guard is the
twin's failure condition. Functions whose call closure aborts only with class
`0` (1479 of 1790) claim nothing, by a check of the program text
([`checkerProg_nv`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/NoVerdictClosed.lean#L235-L236)).

### 4.5 The composition

[`drv_outcome`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/DrvAbi.lean#L181-L192)
is the driver on the machine: `ca_start` calls entry 1, whose setup stub builds
the layout and enters the trampoline, so `compile_correct` gives one L run of
`check` in mode 3 (a run of the compiled, inlined program, which is a run of
the program, §8.6); if that returns `2^63 + k`, it calls entry 2 in place, a
second L run in mode 2 on the memory the first left; if the machine reports
accept, both L runs did.
[`checkerFile_drv_accepts_regs`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/DrvFinal.lean#L104-L110)
composes it with `drv_twinAccepts` for the committed file, and
`EndToEnd.lean` states the four final theorems from it, and the threaded mode's three.

The runs of `check` are the twin's binary in miniature: `check` dispatches on
the mode word ([`checkL`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Entry.lean#L155-L165)),
entry 1 runs the stages and builds the stream index (quoted in §5.1), entry 2
runs the jobs, and modes 4, 5 and 6 are the three runs of `--compare` (§1.2):
the challenge's parse; the solution's parse, preparation and index; and the
challenge's preparation, side records and index with the solution's index moved
aside ([`check_c1`‥`check_c3`](ConAgua/Checker/CompareEntry.lean)).

## 5. L in detail

### 5.1 An example

Entry 1's function, beside the twin function it cites
([L](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Entry.lean#L114-L133),
[the twin](https://github.com/leanprover/con-agua/blob/master/vendor/con-ron/ConRon/Arena/Main.lean#L166-L203),
[its check phase](https://github.com/leanprover/con-agua/blob/master/vendor/con-ron/ConRon/Arena/Checker.lean#L101-L111)):

```
def checkAL : FunDecl := lfn (c) locals (r, z, cnt) {
  z := call cap_check();
  z := call pb_check();
  z := call presize_tables();
  z := call intern_reserved_pins();
  z := call builtin_prelude();
  r := call front_run();
  if r != 0 { return 1 };
  z := call prepare_prelude();
  z := call intern_all_pins();
  cnt := L.Front.DECL.u64[0];
  z := call build_index(cnt);
  z := call par_compact(c);
  return 9223372036854775808 + cnt
}
```

`cap_check` aborts unless the capacities meet the relations' minimums;
`pb_check` compares the pin buffer's startup data with the program's own copy;
`presize_tables` sizes three cons tables from the input length (§6.2).
The rest is the twin's pipeline (`runPipelineHead`, then `runPipelineTail` up
to its check phase), then the first half of the check phase, the stream index
(`build_index`, the twin's `buildIndex`), then `par_compact`, which writes the frozen buffer's
header (with `c ≠ 0` also its images, §9.1). Every callee either returns into
the next line or aborts, and the last line returns `2^63` plus the number of
records: one job each, the second half, which entry 2 runs. `check` itself only dispatches on the global `MODE`, which the
entry stubs write (§9); a zero region leaves it `0`, and then `check` aborts.

A function closer to the data, which decodes a level-list handle
([L](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/LevelEquiv.lean#L136-L141),
[the twin's `viewLs`](https://github.com/leanprover/con-agua/blob/master/vendor/con-ron/ConRon/Arena/Monad.lean#L494-L500)):

```
def lsNode : FunDecl := lfn (h) locals (t, i) {
  if h >> 28 != 0 { abort };
  (t, i) := node LVLS⟦h⟧;
  return (LVLS⟨t, i⟩.o, LVLS⟨t, i⟩.l)
}
```

The tag of a handle (§6.1), then its checked node read: `(t, i) := node LVLS⟦h⟧`
is shorthand for the four statements `t := ⟦h⟧.tier; i := ⟦h⟧.idx;
if t != 0 && CTL.u64[1] == 0 { abort }; if LVLS⟨t⟩.count <= i { abort }`: the
tier and index of the handle, checked against the scratch flag `CTL[1]` and the
store's per-tier node count. Then two fields of node `i` of tier `t`.
The twin fails on a dangling handle; L aborts at the same point.

### 5.2 Syntax and semantics

The abstract syntax
([`Expr`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Syntax.lean#L118-L148),
[`Stmt`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Syntax.lean#L174-L213),
[`FunDecl`, `Prog`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Syntax.lean#L215-L225)):
expressions have no side effects and make no calls, and only an array read can
fail; conditions are a separate type with short-circuit `&&`/`||`, so a guard
like `i < len && b[i] == c` cannot read out of bounds; a call is a statement
and can bind several results. Arithmetic wraps; there is no division (Kraken
has no `div`), only `mulhi`, the high word of the 128-bit product.

The concrete syntax is a set of Lean macros that produce these terms
([the rules](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Notation.lean#L83-L174),
[`lfn`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Notation.lean#L481-L482),
[summary](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Notation.lean#L11-L71)).
Informally (`A` an array, `R` a store, `f` a function, `x` a local or a global,
all names of Lean constants except the locals):

```
fun    ::= lfn (x, …) locals (x, …) { stmt; … }            -- params, then other locals
stmt   ::= x := e  |  x += e  |  x -= e
         | x := call f(e, …)  |  (x, x, …) := call f(e, …)  -- callee's results, 0 if fewer
         | A.u8[e] := e  |  A.u64[e] := e  |  A⟨t⟩[e] := e   -- stores; t a tier word
         | A⟨t⟩.u32[e] := e                                 -- low 32 bits, packed (§5.3)
         | R[e].fld := e  |  R⟨t, e⟩.fld := e               -- record fields
         | if c { … } [else { … }]  |  while c { … }  |  break
         | return e  |  return (e, e, …)  |  abort  |  abort R  |  fail R  |  skip
         | copy!(A[⟨t⟩], e, B[⟨t⟩], e, e)                  -- n words (or bytes), ascending
         | x := scan!(A.u8, e, e, C)                        -- first byte in class C
         | ⟪block⟫                                          -- a named block
         | (x, x) := node R⟦e⟧                              -- checked node read (sugar)
         | for x < x { … }                                  -- counted loop (sugar)
e      ::= n  |  'c'  |  x  |  (e)  |  e op e  |  mulhi(e, e)  |  u64(c)
         | A.u8[e]  |  A.u64[e]  |  A⟨t⟩[e]  |  D.c8[e]        -- loads; D constant bytes
         | A⟨t⟩.u32[e]                                      -- packed 32-bit element (§5.3)
         | len(A.u8)  |  len(A.u64)  |  len(A⟨t⟩)
         | R[e].fld  |  R⟨t, e⟩.fld  |  R⟦h⟧.fld  |  R⟨t⟩.count -- store records, by handle h
         | ⟦h⟧.tier  |  ⟦h⟧.idx  |  A⦃a⦄  |  ⦃a⦄.tier         -- handle and pool-address parts
         | le64!(A.u8, e)                                   -- little-endian word of 8 bytes
op     ::= *  |  +  |  -  |  <<  |  >>  |  &  |  ^  |  |      -- wrapping, on 64-bit words
c      ::= e == e  |  e != e  |  e < e  |  e <= e  |  e > e  |  e >= e  -- unsigned
         | e <ₛ e  |  e ≤ₛ e  |  c && c  |  c || c  |  !c         -- signed; short-circuit
```

The two sugar statements stand for plain ones and give the same terms
([`desugar`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Notation.lean#L337-L363)):
`(t, i) := node R⟦h⟧` is the checked node read of §5.1, and `for j < n { … }`
is `while j < n { …; j += 1 }`, where the body assigns neither `j` nor `n`. The
model generator reads L text through the same function. A counted loop has a
loop rule proved once
([`Triple.forUp`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/For.lean#L72-L88)):
an invariant that each iteration keeps gives the loop's spec, without an
induction on the fuel.

What is absent is absent on purpose: no pointers and no address arithmetic
across arrays (an array is a static index, an access is bounds-checked), no
heap allocation (the arrays are fixed for a run), no closures or function
values (L is first order), no exceptions besides `abort` (which carries a code:
`abort R` the reason constant `R`, `fail R` a reject or decline site, §1.2),
and no division.

The semantics
([module doc](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Semantics.lean#L7-L21)):
the state is the memory and the current frame's locals; every failure is an
[`Err`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Semantics.lean#L47-L57)
(`outOfFuel`, `oob`, `noFun`, `abort k` with the abort's code `k`), never a
result, so no failure can be
read as accept. Fuel is Kleene iteration: `exec p n` is the `n`-th iterate of
the one-step interpreter, and fuel bounds the nesting of loop iterations and
calls along a path
([`exec`, `run`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Semantics.lean#L448-L455)).
A partial-correctness triple has exception postcondition `⊤` and is proved by
induction on the fuel, without ever mentioning it.

**The memory model**
([`Mem`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Semantics.lean#L25-L34)):
three total maps: byte arrays by name, word arrays by name and tier
(`TieredArray`, §5.3), and globals. Every array exists, possibly empty, so an
access to an array a run never filled is out of bounds. Arrays are disjoint by
construction, because they are different keys, and their lengths are fixed for a run. L has
no addresses: an array's number is a name, not a position in memory, and where
the arrays live is the compiler's choice (§8.1). This is the whole memory
story: there is no separation logic, because there are no pointers; "disjoint
and in bounds" is proved once, by the compiler (§8.2).

### 5.3 Tiered arrays

con-ron keeps a persistent and a scratch tier of every table (§6.2). A word
array of L's memory is a `TieredArray`: tier `hi` of array `arr`. A plain
access names tier 0 (`↑a`); an access with a run-time tier word `t` names
`tierA a t`, the tier masked with `1`
([`TieredArray`, `tierA`, `tiers`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Syntax.lean#L29-L84)):
`A⟨t⟩[i]` in the surface syntax. Tier 1 of `a` is `tier1 a`, both tiers are
`tiers a`, and distinct arrays and the two tiers of one array are distinct keys
by construction, with no numbering involved. The compiler puts tier 1's
descriptor right after tier 0's, so a tiered access costs one indexed load more
than a plain one (§8.1). The node stores are accessed through
[record accessors](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/TRec.lean#L7-L31)
(`R⟨t, i⟩.f`, `R⟦h⟧.f`, `R⟨t⟩.count`), which fix the layout in one place.

A tiered word array also holds 32-bit elements, two per word: `A⟨t⟩.u32[i]`
reads element `i`, half `i % 2` of word `i / 2` (the low half first, the
machine's little-endian layout), and `A⟨t⟩.u32[i] := e` writes the low 32 bits
of `e` there and keeps the other half. The memory stays words: in the semantics
the store is a word store of the word with one half replaced. The compiler emits
one 4-byte move for each (`movl`, at byte `4 i` of the array), after one compare
of `i` with the array's length in 32-bit elements, which the descriptor table
keeps beside its length in words (§6.4), and its proof
rests on one lemma about Kraken's byte memory: the 4 bytes at `X + 4h` of the
word at `X` are its half `h`, and a 4-byte store there leaves the memory an
8-byte store of the word with that half replaced leaves. With a constant tier
(`A⟨0⟩.u32[i]`) the access may name an untiered array: the id tables keep their
dense entries so. A packed record's field, one half of a word, is read alone too
(`Expr.ld32h`, emitted by the record accessors): the word load's bounds check,
then the 4-byte load of the low or the high half.

### 5.4 Block primitives

Three primitives do in one statement what a loop would do word by word, with
the bounds checked once
([`le64!`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Notation.lean#L106-L107),
[`scan!`, `copy!`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Notation.lean#L159-L165)):

* `copy!(D, di, S, si, n)`: copy `n` words (or bytes, zero-extended into
  words) from `S` to `D`, ascending;
* `x := scan!(A.u8, i, e, C)`: the first position in `[i, e)` whose byte is in
  the class `C` (a 256-byte table, constant data), else `e`;
* `le64!(A.u8, i)`: the little-endian word of eight bytes.

Their semantics are ordinary Lean functions
([`le64`, `Mem.copy64`, `scanN`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Semantics.lean#L207-L226)),
and the compiler emits a tight loop for each: six instructions per copied word,
seven per scanned byte
([`copy64Code`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L1046-L1057),
[`scanLoop`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L1079-L1086)).

## 6. Data structures and memory layout

The twin's state is con-ron's: hash-consed stores of expression, level, name
and level-list nodes per tier, per-call memos, per-declaration caches, the
environment, the pins. L represents each piece by word arrays, and a relation
says how (§7).

### 6.1 Handles

A handle is con-ron's 32-bit word, held in a 64-bit word, in one of two shapes: the tier in
bit 31; bit 30 set for an expression `app` (wide: the node index in bits 29–0), clear for every
other node (narrow: the constructor tag in bits 29–26, the node index in bits 25–0)
([`tierE`, `idxE`, `idxAE`, `tagE`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/TRec.lean#L113-L148)).
Equal terms have equal handles (hash-consing), so comparing two terms is
comparing two words.

### 6.2 Stores, cons tables, the two tiers

Each store keeps, per tier, one word array of fixed-size records (node `i` of
tier `t` at `arr⟨t⟩[i * w ..]`) and its node count in a control word; the
stores and their fields are declared in one file,
[`ConAgua/Arena/StoreFields.lean`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/StoreFields.lean#L13-L36).
A store whose two key fields are handles packs them into one record word.

Each store's **cons table**, the hash map from a node's fields to its handle,
is con-ron's key-free `ConsMap`: open addressing, linear probing, one table per
tier in its own word array, growth at load 3/4. A slot is one word, the node's
value (`B + i + 1` for node `i`, below) and a 16-bit fragment of its key's hash;
the key itself is read from the node's record, and only on a slot whose fragment
is the query's
([the layout](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/ConsLib.lean#L221-L233),
[the growth test](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/ConsLib.lean#L570-L575)).
Where con-ron allocates a table of twice the size and frees the old one, L
doubles the table **in place**: it zeroes the upper half, then one top-down
sweep re-inserts each live entry from its new home with a probe that stays
above the sweep; the few entries that probe cannot place are marked and
re-inserted by absl's in-place swap loop over the ranges that hold marks
([`kgrowB`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/ConsLib.lean#L541-L561)),
since L cannot free memory. The home slot is `mulhi(mix(h), n)` rather than
con-ron's mask
([`homeW`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/SlotGrow.lean#L41-L44)).
Both are deliberate deviations, verdict-neutral (D36, D38). The persistent
tiers of the three tables the parse fills most (`app`, `lam`, `forallE`) start
at a slot count computed from the input length
([`presize_tables`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Presize.lean#L48-L59)),
so the parse does not double them; the memory is all zero there, so the
larger table costs nothing until it is used. con-ron's tables start empty
(D42, also verdict-neutral).

The **scratch tier** holds what one declaration's check creates. It is emptied
in O(1) per table: a scratch slot's value is `B + i + 1` for node `i`, and reads as
free at or below the slot base `B`, so raising `B` empties every scratch table
without writing a slot (con-ron's epoch stamps; ours are 15 bits, so every
32 766 resets the scratch tables are zeroed, D43)
([`scratch_reset`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/Scratch.lean#L18-L37)).
Nothing moves from the scratch tier to the persistent one: what a record's job
creates, the constants of an inductive block included, stays in the scratch
tier and is dropped with it, as in con-ron.

The **memos** (con-ron's per-call maps) are one generic library: a schema names
the array and the stamp word, four words per slot, epoch stamps, growth at load
3/4
([`MemoLib`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/MemoLib.lean#L20-L50)).
The put is one leaf function whose growth reuses its locals, so that the leaf
register allocation keeps the common case, an insertion without growth, in
registers
([`memoPutG`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/MemoLib.lean#L435-L462)).
A clear is an epoch bump, after which the table restarts at its default region;
`inst_list`'s memo clears as con-ron's `clear_fit` instead: the next call's
region is sized from a decaying high-water mark of the entries, kept in the
header slot
([`X_clear_fit`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/MemoLib.lean#L649-L660)),
and the caller makes the common case (no mark, a small call) the epoch bump
alone
([`inst_list`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/InstListSpec.lean#L98-L103)).

### 6.3 The limb pool

con-ron's `Nat` is a `Vec<u64>` of limbs. In L every number, every name's bytes
and every level list's handles live in one tiered word array, the **pool**, as
a slice `(offset, length)`; the pool grows at its top, and nothing below the top
is written again, so every slice stays valid
([the pool](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/Pool.lean#L12-L31)).
A slice address carries its tier in bit 40. The scratch tier's slices are
dropped with the scratch tier; within one declaration the pool only grows
(deviation D10).

The environment's records (con-ron's constant, inductive and recursor infos)
live in a second pool of the same shape, `EREC`, with tier-tagged addresses:
tier 0 holds the stream index's and the pins' records, tier 1 a job's own (a
block's pushes, a gate's temporary record), emptied when the next job starts.
The environment a job sees is con-ron's: the job's own layer (its own index of
the constants and projection tables it pushed, whose rows carry the job's
stamp, so a job starts empty without clearing) over the stream index, read at
the index's view of the job's position (two control words the job sets)
([`Arena/Env.lean`](ConAgua/Arena/Env.lean)).

### 6.4 The region

At run time every array lives in one region the harness maps
([the entry stub](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Abi.lean#L8-L41)).
The region is a static partition into slots of `2^35` bytes: slot 0 holds the
descriptor table (a base, a length and a length in 32-bit elements per
descriptor position, the constant data, the globals), slot 1 the L stack (1 GiB at its bottom), then one slot per
array, each array getting its whole slot (`2^32` words). The input and the pin
data are the caller's buffers, at descriptor positions 0 and 1, and have no
slot. The other exception is the control words `CTL` (marked `at table` in the
array table): they live in slot 0, past the table, with a fixed length of 256
words; they have the last position, which gets no slot. There is no allocator:
the pages a run never touches never become real (`MAP_NORESERVE`), so the
capacities cost address space, not memory. The checker has 184 descriptor
positions (2 byte arrays, 124 word arrays of which 58 are tiered, so 182 word
positions), a descriptor table of 4 432 bytes, and 183 slots, about 5.7 TiB
of address space (`ca_region_size` in `checker.s`).

**The arrays.** Every array of the checker is declared once, in one table
([`checkerArrays`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Layout.lean#L48-L54)): its
name, its kind (byte or word, in one name space: no two arrays share a number), whether it is tiered,
its number and, for some word arrays, a minimum length (§8.1). The number is a name: the table is the list of arrays, not the
layout. `Checker/ArrCheck.lean` checks it against the program and the compiler
([the checks](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/ArrCheck.lean#L33-L42)):
the numbers are distinct; a byte access names a byte array of the
table, a tiered access a tiered array, and a plain word access a word array of
the table
([the surface check](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Arrays.lean#L230-L233));
the compiler's layout has a position for every array of the table; and the
parallel mode's frozen and owned arrays are arrays of the table.

**The layout.** The compiler maps each array of the table to a descriptor
position, the byte arrays first, then the word arrays in table order, tier 1 of
a tiered array right after its tier 0 (§8.1)
([`checkerTabOf`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/ProgTab.lean#L19-L30)),
and the entry stub gives position `p ≥ 2` slot `p`. The harness reads the layout only
through the symbols the stub exports (`ca_region_size`, `ca_slot`, …), so it
does not know the arrays at all.

Where L's representation differs from con-ron's beyond layout, it is listed in
[`docs/deviations.md`](docs/deviations.md) (§10.2).

## 7. How the L ↔ twin proofs are written

### 7.1 Three layers per function

Take `lvl_eq`, the uncached core of the twin's `lvlEq?`:

1. **The L code**, with its citation and census tag
   ([`lvlEqL`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/LevelEquiv.lean#L107-L117)).
2. **A word model and a spec.** The model `lvlEqW` is the L code as a Lean
   function on `Mem` and words, `none` where L aborts; the spec says a run of
   the function is the model. Both are generated from the `lfn` by `l_model`,
   which also proves the spec (`vcgen`, then `grind` over the model's
   equations)
   ([`lvlEq_spec`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/LevelEquiv.lean#L119-L124)).
3. **The refinement**: under the arena relation, a model that returns `z`
   gives a twin run of `lvlEq? u v` that succeeds with the result `z` encodes,
   and the relation holds again
   ([`lvlEq_refines`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/LevelArena.lean#L266-L271),
   against [the twin](https://github.com/leanprover/con-agua/blob/master/vendor/con-ron/ConRon/Arena/Core.lean#L168-L185)).

The split keeps `vcgen` away from the twin's monad and the twin's proofs away
from L's syntax. Most word models and specs are generated: the `l_model`
command reads a group of `lfn`s and produces the models, one guarded equation
per arm for `grind`, and the specs with their proofs
([`ConAgua/L/ModelGen.lean`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/ModelGen.lean#L12-L65);
204 uses). Two habits keep the proofs fast: facts are guarded equations about
named functions (no `∃`, disjunction or `fun` in a postcondition), and each
path is proved by plain `vcgen`, then `vc_flat` (the intermediate states out of
the condition) and `grind`, not by `finish` on every path.

### 7.2 Relations and encapsulation

The relations nest by scope: one per store (`LitR`, `AppR`, …), the arena
relation over all stores, the pool and the memos
([`ArenaR`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/ArenaRel.lean#L285-L308)),
the core relation with the caches, the stage relation of the declaration
checks, the loop relation of the fold. A refinement is stated at the smallest
relation that suffices and lifted.

Data structures are abstract. The cons tables are one library, generic in a
schema, whose relation `ConsR` is `irreducible` outside its file; users see
lemmas for reading, keeping and interning, never the slots
([`ConsLibRel`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Arena/ConsLibRel.lean#L11-L31)).
Likewise the records are read through `tfld`/`tcnt`, and the layout
(`TRec.ad`) stays folded.

### 7.3 Frames and non-interference

Which arrays a function writes is computed from the program text: a `Bool`
check that a call-closed set of functions stores only into given arrays and
control words gives a frame lemma for all of them
([`ConAgua/L/WriteSet.lean`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/WriteSet.lean#L14-L31)).
Scripts regenerate the closures (`scripts/core_fns.py`, `loop_fns.py`,
`leaf_fns.py`, `preloop_ws.py`, `phaseb_fns.py`) and the build fails when one is
stale.

The dual, for reads: if a function set names only arrays in a set `S`, two runs
from memories that agree on `S` end the same way
([`run_agree`](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Agree.lean#L600-L604),
[the idea](https://github.com/leanprover/con-agua/blob/master/ConAgua/L/Agree.lean#L7-L31)).
The parallel mode uses it to run the jobs on a memory that has only the frozen
arrays and the worker's own (§9).

### 7.4 Composition

Each stage of `check` is a relational spec
([`RelSpec`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Pipeline.lean#L49-L53)):
from memory related to the twin's state before the stage, a returning call ends
in memory related to the state after the twin's stage. The stages are proved at
the checker's program and chained into entry 1's run; the last one, the
stream index's build, is
[`buildStage_checker`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/BuildStage.lean#L307-L313).
The twin's mutual recursion (whnf, defeq, infer) runs on fuel; the L side
proves its refinement at every twin fuel at least the L fuel
([`InputsOK`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Pipeline.lean#L74-L77) bounds only the sizes; the fuel is free).

## 8. The compiler and its proof

### 8.1 Code generation

One pass, no register allocation for non-leaf functions
([conventions](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L9-L34)):
`r15` holds the descriptor table, `r14` the fuel (decremented at every loop
back-edge and call), `rsp` the frame (locals and temporaries), `rbp` the
trampoline's saved stack pointer. An expression is evaluated straight into its
target register (the local's register, a result or argument register, or
`rax`), its intermediate values in scratch registers (`rax`, `rcx`, `rdx` and
the argument registers that hold no local); registers, memory words and
constants are used in place as operands, and a constant index is folded into
the address. Expressions this does not cover go through `rax` with their
intermediate values in frame temporaries. An
array access loads the base and length from the table and branches to
`ca_error` when out of bounds; a constant index below the array's minimum length
(a hint in the array table, `min k`) needs no bounds check, nor does an index that the
bounds-check analysis proves in range (§8.7), and the array marked
`at table` is addressed from `r15` at a fixed offset, with no load of its base; so is a byte of
the constant data (`ldc`), checked only when the analysis does not bound its index below the
string's length. The trampoline saves the callee-saved registers
(`rbp`, `r14` and the table address on the machine stack; `r15`, `rbx`, `r12`,
`r13` in the 32 bytes past the table), restores them on every exit, and maps
the outcomes to `rdx`, so the code generator may use any register
([`trampoline`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L2138-L2159)).

The local optimisations, all inside the proof: a comparison of two simple
operands (a register, a memory word, a constant) is one `cmp`, its operands
swapped when the left one is a constant; `x := x op e` updates `x` in place; a
local is zeroed on entry only if it may be read before it is assigned; a leaf
function keeps its locals in nine registers
([`allocRegs`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L804));
the tier local of a leaf stays in `rsi`; a leaf with a frame, other than the
entry, checks no stack limit: its callers' checks leave room for its frame
([`compileFn`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L2109-L2121)); a tiered access finds tier 1's
descriptor at a fixed offset after tier 0's.

**The layout map.** Only the compiler knows where arrays live. Byte and word
arrays share one position space, each position with an element kind: the
byte positions come first, then the word positions. The layout map is a search
tree from an array's name to its position, stored in the table with its inverse
(the array at each position), and the table carries a `Bool` check that the two
agree, that the kinds are right and that tier 1 of a tiered array sits right
after its tier 0
([`layOkB`, `Tab`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L99-L160),
[`dom8`, `pos8`, `dom64`, `pos64`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L170-L182)).
The definitions are irreducible past their lemmas, so no simulation proof
reads a position. `Prog.wf` checks every operand against `dom8`/`dom64`, which
also checks its kind.

### 8.2 The proof

A forward simulation on Kraken's `Eventually`, one lemma per instruction form
in continuation-passing style
([`Step.lean`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Step.lean#L11-L19)),
then expressions, statements, calls, functions and blocks (`SimExpr` …
`SimBlock`), composed by induction on the fuel and then on the statement
(`execSim_all`). The relation is
[`MemRel`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Rel.lean#L144-L167),
which relates L's array `s` to the machine region at position `pos s`, for
every `s` in `dom`, under a layout whose regions are in the address space and pairwise disjoint
and which gives every array at least its minimum length and the table-relative
array its fixed offset
([`Layout.Ok`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Rel.lean#L71-L85)).
Well-formedness of a program (`Prog.wf`) is a `Bool` check, evaluated by the
kernel through a fast variant keyed by name codes.

### 8.3 The entry stub

The setup stub `ca_setup` is emitted before the trampoline; the entries jump to
it with `ca_start`'s arguments. It checks the region size and that
`in_len` and `pins_len` are below `2^63` (returning `rdx = 1` otherwise, as for
a small region), writes
the descriptor table for the static partition (§6.4) and the constant data by
immediate stores, and enters the trampoline with fuel `2^62 - 1`
([the stubs](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Abi.lean#L8-L41)).
Its proof (`sim_abiStub`, `abiLayout_ok`, `abi_memRel`) shows that it
establishes `Layout.Ok` and `MemRel`, so the harness only maps zeros. Every
array gets a whole slot there, so every minimum length holds; the table-relative
array gets its minimum length, at the offset the code addresses. The stub puts
the caller's two buffers at descriptor positions 0 and 1; that the layout map
has the input and the pin data there is a `Bool` check on the checker's table
that only the stub proof uses (`abiIO`).

### 8.4 The committed file, checked by the kernel

The final theorem is about `checker.s` itself.
[`checkerFile`](https://github.com/leanprover/con-agua/blob/master/ConAguaAsm/Checker.lean#L22-L23)
is the file's code as `include_asm` reads it at elaboration time; Lake rebuilds
it when the file changes. Then
[`checkerFile_eq`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/AsmFileEq.lean#L29-L30)
proves `checkerFile = checkerStub ++ checkerAsm`, where `checkerAsm` is a
literal that the kernel checked, function by function, to be
`compileProgX checkerX checkerTab checkerProgI "check"` (§8.6; `checkerX`:
the hand-written bodies, §4.2)
([`Checker/Asm.lean`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Asm.lean#L42-L51)).
So neither the compiler run as compiled Lean code nor the printer that wrote
the file is trusted; a stale file fails the build, naming the first function
that differs.

What is trusted is the parser
([`include_asm`](https://github.com/leanprover/con-agua/blob/master/ConAgua/AsmFile/Include.lean#L17-L36)),
with two checks around it: it prints the code back with Kraken's printer and
compares with the file's lines, and
[`CrossCheck.lean`](https://github.com/leanprover/con-agua/blob/master/ConAgua/AsmFile/CrossCheck.lean#L12-L18)
reads the file with Kraken's own parser, which `scripts/asm_file.py` runs.

### 8.5 Regenerating the committed files

`checker.s` and `pins.bin` are generated from the Lean sources and committed,
so that building the binary needs no Lean (§1.1). After a change to the
checker's L code, the compiler, the entry stubs or the startup data:

```
make regen          # python3 scripts/asm_file.py: rewrite checker.s and pins.bin
make regen-check    # fail if either committed file is stale
```

([what it does](https://github.com/leanprover/con-agua/blob/master/scripts/asm_file.py#L2-L21);
`pins.bin` is `scripts/lake exe romgen pins.bin 4`,
[`ConAgua/Rom/Gen.lean`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Rom/Gen.lean#L18-L27)).
Regeneration is a convenience, not part of the trust: the build fails at
`checkerFile_eq` if `checker.s` is not exactly the compiler's output (§8.4),
and the theorem holds at every pin-data buffer.


### 8.6 Inlining

[`inlineProg`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Inline.lean)
replaces each call of a leaf function (one whose body makes no call) of at most
80 nodes by the callee's body: its locals shifted past the caller's (all inlined
calls of a function share one region), the locals it may read before it assigns
them zeroed, its parameters set from the arguments, and its exits turned into
assignments to the call's result locals. The conversion passes the rest of the
body as a continuation, so a `return` drops it and an `if` whose one branch
always exits gets it in the other branch only; a body it cannot convert (an
`if` with exits that does not always exit, a `return` in a loop) stays a call.
On `Init` it saves 2.1 % of the instructions.

[`inlineProg_run`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/InlineCorrect.lean):
a run of the inlined program that does not run out of fuel is a run of the
original with the same results and memory, or the same error, with one more unit
of fuel per round (an inlined body runs at its caller's level of fuel; it is a
leaf, so this never compounds). The entry stubs pass `abiFuel - 1` to the
trampoline, so the final theorems still speak of `checkerProg` with `abiFuel`
([`compile_correct_frame_ref`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/MainRef.lean)).
The kernel does not run the pass over the whole program: the inlined program is
a literal (`checkerProgI`), one kernel-checked equation per function
([`inl_round_fns`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/InlineLit.lean)),
which the whole-program checks of the compiled code then read.

### 8.7 Bounds-check elimination

A forward analysis of each function body, with no knowledge of other functions,
computes at each statement facts about its locals: `i < len(A)` for an index
expression `i` built from locals, constants and operators, and upper bounds
`x < n` of locals
([`postF`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Bce.lean#L234-L258)).
A fact comes from a condition, in the branch where it holds; from an access
that ran (it passed its check); and from an assignment of a bounded expression
(constants, `&`, `>>` by a constant, `+` that cannot wrap). A write to a local
removes the facts that read it; a loop's condition and body see only the facts
that read no local the body writes. An access whose fact holds, or whose index
is bounded by the array's minimum length, is emitted without its bounds check
([`Ctx.ck`, `chkR`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Compile.lean#L838-L844)).
This covers the loads and stores of the register-stack code generator; the
other accesses keep their checks.

The proof is part of the compiler's: every run of `exec p n` keeps the arrays'
sizes and the locals a statement does not write, and ends a statement normally
only with the facts after it true
([`fsound_exec`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/BcePost.lean#L436-L441));
the statement simulation carries the facts of the current statement, the
expression simulation those of the statement's state on the locals the
expression reads
([`FactsFor`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/BceSound.lean#L582-L586)),
and an access without its check takes the index bound from them
([`ck_sound`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/BceSound.lean#L629-L641)).
Measured on `Init` (2026-10-30, exact counts): the analysis removes 1,244 of the
7,986 bounds checks from `checker.s`, 28.5 % of the checks executed and 1.9 % of
the instructions.
## 9. Parallel checking

con-ron runs the records' jobs on worker threads that share the stream index and
the persistent tier read-only; each worker runs the jobs it claimed, in
increasing order, on one state it threads through them
([con-ron's pool, as the twin states it](https://github.com/leanprover/con-agua/blob/master/vendor/con-ron/ConRon/Arena/Pooled.lean#L20-L46)).
con-agua does the same with two entry points and a frozen buffer; the
sequential driver `ca_start` runs the same two entries one after the other
([`check` and its entries](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Entry.lean#L105-L112)).

### 9.1 The two entries

* **Entry 1** (`ca_start_a`, `check` in mode 1): the stages and the stream
  index, then `par_compact` writes the **frozen buffer** into the word array
  `OUT`: a header and a prefix image of every array the jobs read (the stores'
  persistent tiers, their slot tables and columns, the stream index, the record
  pool's tier 0, the pins, and the parsed records, since a job reads its own);
  it returns `2^63 + k` for `k` records
  ([`check_a`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Entry.lean#L114-L133)).
* **Entry 2** (`ca_check_b(buf, len, j, region, region_len)`, mode 2): a stub
  gives each frozen array a descriptor into the buffer, each array the jobs
  write a slot of the worker's own region, and every other array length 0;
  it declines (`rdx = 1`) if a frozen array in the buffer is shorter than its
  minimum length; then `check_b` flushes the core caches (a worker of the twin
  starts with empty caches) and runs job `j`
  ([`check_b`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/Entry.lean#L135-L153)).
  Later calls on the same region continue from the state the previous call
  left, as con-ron's worker state is threaded through its jobs.

### 9.2 The sequential driver: `ca_start`

`ca_start`, the entry the harness calls without `--jobs`, runs entry 1 in mode
3 (the buffer's header only), then one entry-2 run over all jobs `[0, k)` in
place, on entry 1's own arrays, so it needs the setup stub's region plus 16
bytes, where it keeps its return address and the caller's `r15`
([the driver](https://github.com/leanprover/con-agua/blob/master/ConAgua/Compiler/Abi.lean#L225-L234)).
Its machine-level theorem
([`drv_outcome`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/DrvAbi.lean#L181-L192))
says that an accept means the two L runs accepted, and an error report
(`rdx = 2`) that one of them failed with the code in `rax`;
[`drv_twinAccepts`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Checker/ParDriverTwin.lean#L101-L111)
that two such runs mean `TwinAccepts`; the final theorems (§2.1) compose them
for the committed file.

### 9.3 The threads

`--jobs=N` (`run_jobs` in the harness): after entry 1 the harness unmaps the
rest of the region around the buffer, makes the buffer read-only, releases the
input buffer, and starts `N` threads; each maps its own zero region and claims
job indices from one atomic counter, calling `ca_check_b` for each, until a
call does not accept
([the harness](https://github.com/leanprover/con-agua/blob/master/main.c#L169-L187)).
Accept iff every call accepted; otherwise the verdict is that of the failing
job with the smallest index, as the sequential run reports it. L has no atomics: each call is an ordinary
sequential L run, and the claiming is the harness's.

[`checkerFile_threads_accept`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/EndToEnd.lean#L157-L160)
covers this mode for the committed file: if the harness behaves as
`ThreadsRun` says (§2.3), every call accepts and the threads claim every job
index, each thread in increasing order, then the twin's pipeline accepts `b`
with the check phase as con-ron's pool
([`TwinAcceptsPooled`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/TwinPooled.lean#L39-L47)),
and the model and no-`False` corollaries follow as in §2.1. Its pieces: entry
1's run with the frozen buffer it leaves, a fresh worker's start state over the
buffer and a zero region, and one job per call of entry 2, each a sequential
L run related to con-ron's worker by non-interference (§7.3).
[`checkerFile_threads_regs`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/EndToEnd.lean#L165-L169)
adds that entry 1 and every `ca_check_b` call return with the caller's
callee-saved registers intact.
[`checkerFile_threads_verdict`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/EndToEnd.lean#L178-L181)
covers a failing run: if the harness behaves as `ThreadsFail` says (§2.3) and
the reported code has class `1` or `2`, the twin's pool fails with that class
([`TwinVerdictPooled`](https://github.com/leanprover/con-agua/blob/master/ConAgua/Final/TwinVerdict.lean#L189-L203)):
the pipeline fails before the jobs with that class (`TwinVerdict`), or the
stages and the stream index ran ok and the failing thread's jobs, in the order
it claimed them, fail from the index state's worker with that class. A job's
check needs con-ron's fold invariant at the job's view, which needs every
record below it accepted; the threads' accepting calls below the failing job
give it (the induction of con-ron's `pooled_fold`, up to the failing job,
[`pool_prefix`](ConAgua/Arena/PoolJobs.lean)). This is the pool's form of the
sequential verdict, not `TwinVerdict` itself: con-ron proves nothing that
takes one worker's failing list to the sequential run's verdict (a job's
result from a worker's state equal to its result from the sequential run's
state).

On 2026-11-13 (con-leche `ca6af099`, con-ron `c78714ac`), `ca_start` agreed
with con-leche's pinned verdicts on all 726 fixtures `scripts/diff-e2e.py`
compares (§10.3), sequentially; it skips the seven fixtures con-leche runs with
command-line flags the checker does not take (the smaller maximum `Nat` size,
[docs/deviations.md](docs/deviations.md)).

## 10. Keeping the port honest

### 10.1 Close twin, citations, census

L is a close twin of con-ron: it computes what the twin computes, the way the
twin computes it, data structure for data structure. Every L function carries a
citation line naming the twin code it stands for, at the vendored revision
(`-- con-ron: ConRon/Arena/Core.lean:137-154 ConRon.Arena.lvlEq?`, or
`con-ron: none — <reason>` for plumbing);
`scripts/provenance.py check` verifies them, and `scripts/bump-con-ron.sh`
moves them when the twin is re-vendored and marks the code whose twin changed;
`scripts/bump-con-ron.sh --report <rev>` lists, before a bump, the twin
definitions that changed and the L functions and refinement theorems they reach.
`vendor/` is exactly the upstream files at the two revisions plus a patch series
under `vendor/patches/` (`scripts/bump-con-ron.sh --check`).

L functions are tagged `@[l_impl T]` and refinement theorems `@[refines T]`.
`scripts/census.py` lists every twin and con-leche definition `TwinAccepts`
reaches and its status: proved, written, or deliberately not needed (listed
with reasons in [`docs/not-needed.md`](docs/not-needed.md)). The census counts
a target as proved only if its refinement theorem uses no axiom beyond
con-leche's three.

### 10.2 The deviations list

[`docs/deviations.md`](docs/deviations.md) lists every place where L does
something else than the twin, beyond fuel and fixed capacities, in three
sections:
[Temporary](https://github.com/leanprover/con-agua/blob/master/docs/deviations.md#L24-L38)
(to be fixed, or intent unclear),
[Deliberate](https://github.com/leanprover/con-agua/blob/master/docs/deviations.md#L40-L67)
(by design, with the reason), and
[Fixed](https://github.com/leanprover/con-agua/blob/master/docs/deviations.md#L70-L99).
Each row says what the twin does, what L does, and the effect: completeness (L
declines where the twin accepts), performance, or none. No deviation may lose
soundness, and the theorem would not let one through: it is about the L code as
it is.

### 10.3 Differential testing

`scripts/e2e.py` assembles the checker, runs it on con-leche's e2e fixtures and
the arena tests (777 inputs), and compares each verdict with two references:
the twin compiled by Lean (`con-ron-lean-twin`) and con-ron's Rust binary
([how](https://github.com/leanprover/con-agua/blob/master/scripts/e2e.py#L2-L25)).
`scripts/diff-e2e.py` needs no Lean: it runs the built binary on the 730 of
these inputs that have a verdict pinned by con-leche and compares accept versus
not-accept with it, sequentially and with `--jobs=4`
([how](https://github.com/leanprover/con-agua/blob/master/scripts/diff-e2e.py#L2-L46)).
Seven of them, the `nat_size_limit_*` fixtures, are pinned at a maximum
`Nat` size of 16 bytes (con-leche's test table runs them with
`--max-nat-size=16`); the checker runs every input at the default maximum
(§2.1), so their verdicts are not comparable with the pinned ones, and
`scripts/diff-e2e.py` skips them.
`scripts/diff-e2e.py --refs` also compares the verdicts with con-ron's and
con-ron-lean-twin's (and a reject or decline with con-ron's). These cover what the theorem does not: the harness
and completeness.

### 10.4 The gates

A branch lands on master only after the gates of
[`scripts/gates.sh`](https://github.com/leanprover/con-agua/blob/master/scripts/gates.sh#L11-L24)
pass on its merge with master: `lake build` (which includes the axiom
guards, `checkerFile_eq` and the staleness checks of the generated closures),
the `--check` modes of the closure scripts and of the generator of the checker's program
(`scripts/checker_prog.py`), `scripts/modules_check.py` (every
module is built by some target), the citation check `scripts/provenance.py
check`, the vendor check, `scripts/diff-e2e.py`, the import check `scripts/shake.py` (every
import that Lean's import minimizer, `lake shake`, finds unused is listed in
`scripts/shake-allowlist.txt` with the reason the build needs it), the assembler check
`scripts/check-asm.sh` (§2.3), the warning check
`scripts/lean_warnings.py` (no Lean warning in the changed modules, including those restored from the
shared build cache, whose warnings are kept in a log store beside it), and this document's link gate.
Each merge runs the gates its change can affect
([the table](https://github.com/leanprover/con-agua/blob/master/scripts/gate_select.py#L17-L50)).
`scripts/overview-links.sh` extracts every line-anchored link of OVERVIEW.md
and README.md with the cited lines into
`scripts/overview-links-expected.txt`, and fails when they move or change.

Continuous integration
([`.github/workflows/ci.yml`](https://github.com/leanprover/con-agua/blob/master/.github/workflows/ci.yml#L4-L80))
runs on every push and pull request to master, in two jobs. The `checker` job
needs no Lean: `make`, `make check` and `scripts/diff-e2e.py` (§10.3) on
con-leche's tests at the vendored revision. The `proof` job runs
`scripts/lake build` (the axiom guards and `checkerFile_eq` included) and fails on
any warning in its log that is not Kraken's (`scripts/check-no-warnings.sh`), the
`--check` modes of `scripts/asm_file.py` (`checker.s` and `pins.bin` are what
the generators print) and of the closure scripts, `scripts/check-asm.sh`, `scripts/modules_check.py`,
the link gate, `scripts/bump-con-ron.sh --check` (`vendor/` is the upstream
files plus the patch series), `scripts/provenance.py check` and the import check
`scripts/shake.py`. It caches
`.lake/build` between runs; a cold build took 35 minutes at
`LEAN_NUM_THREADS=4` (2026-10-25, on the development machine).
