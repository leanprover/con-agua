# Lane w32survey: would 32-bit word arrays in L pay? (survey)

**Question** (the user, 2026-10-29). L has byte arrays and 64-bit word arrays only. An array of
32-bit values (handles, indices, derived words) wastes half of every word. Would a 32-bit element
width, declared per array with the layout owned by the compiler (`absarrays.md`, `dense.md`), be
worth designing? This journal covers which arrays fit in 32 bits, what they occupy on `Init`, how
con-ron lays out the same data, what the feature would cost, and the alternatives. No proof
changed. Only this file lands.

Base: master e0a35b28. Scratch: `_tmp/w32survey/`, outside the repository. It holds the
instrumented harness `main_mc.c`, the tabulation scripts `tab.py` and `cat.py`, the prototype
`checker_ader.s`, and the wall bench `wb.json`.

**Answer, in short.**

* **The RSS gap to con-ron is the input file, not word widths.** Of the 748 MB peak RSS on `Init`
  (one thread), **346 MB is the input**: the harness `mmap`s the whole 346 MB export, and every
  page has been read by the end. The word arrays take **406 MB**. con-ron streams the input in
  4 MiB chunks, so its 491 MB is all heap. Our arrays are already 85 MB smaller than con-ron's
  heap.
* **A per-array width alone would save about 29 MB** (3.9 % of the RSS). That covers the arrays
  that hold one 32-bit value per word: the derived words `ADER`/`LADER`/`FADER`/… (52 of those
  58 MB), the environment's row arrays, `PEND` and `ECON`.
* **Every larger saving needs mixed-width records,** a further step beyond a per-array width. A
  cons slot holds a 32-bit value next to a 64-bit key; a memo slot holds a 32-bit stamp, a
  32-bit key, a 64-bit key and a 32-bit value. Packing those as 32-bit fields would save another
  ~45 MB in the cons tables (tier 0) and 11–22 MB in the memos. The total ceiling is about
  **115 MB (15 %)**.
* **Three of the user's examples already use both halves.** `EID` (and `NID`, `LID`) is already
  hand-packed two 32-bit entries per word (`Front/IdTable.lean`, `dnW`). `AREC`, `LAREC`,
  `FAREC`, `CREC`, `MREC` and `IREC` pack two handles per word. Only `ADER` is half empty.
* **Prototype:** `ADER` at 32 bits, hand-edited in `checker.s` (4 instructions, unproved). It
  saves 22 MB of RSS (748 → 726 MB). Wall time on `Init`, one thread, 30 interleaved paired
  rounds under load: median −2.1 % (Wilcoxon p = 0.003), not yet confirmed on a quiet
  machine (§6).
* **Recommendation: do not design the language feature now.** The memory it reaches is small
  next to the input mapping. The one hot half-empty array (`ADER`) can be packed in L the way
  the id tables already are, if a quiet rerun confirms §6's −2 %. Revisit the feature only if several new
  32-bit columns appear, or if mixed-width records are wanted for the cons and memo slots.

## 1. Method

**Per-array resident bytes, exact.** `main_mc.c` is `main.c` plus a block after `ca_start`
returns. The block calls `mincore` on every `2^35`-byte slot of the region and on the input
mapping, and prints the resident bytes and the highest touched page per slot. Peak equals final
here: L never frees memory, and no array shrinks (the scratch tiers are emptied by raising the
slot base, not by unmapping). Slots map to arrays through the layout of `ConAgua/Layout.lean`:
position `p ≥ 2` is slot `p`, the word arrays come in table order, tier 1 follows tier 0, and
`CTL` comes last with no slot. Check: `OUT` lands on slot 179 = `ca_out_off / ca_slot`.

The figures below come from runs with THP off (`W32_NOTHP=1`, which skips `advise_huge`), so
they have 4 KB precision. As shipped (THP on), the interior of an array is 2 MB-rounded: the
arrays total 432 MB instead of 411 MB, and `ru_maxrss` is 769 MB instead of 748 MB. The
`mincore` vector adds about 8 MB to the instrumented binary's `ru_maxrss`. Shipped binary per
OVERVIEW §3: 741–744 MB.

**Where `Init`'s 748 MB go** (one thread, THP off):

| | MB |
|---|---:|
| input mapping (`init435.ndjson`, fully resident at the end) | 345.7 |
| word arrays (180 positions; 149 hold at least one page) | 406.0 |
| L stack (slot 1) | 4.6 |
| slot 0 (descriptor table, globals, `CTL`) | 0.05 |

## 2. The arrays: content, width, `Init` bytes

The classes:
* **A**: one value per word, and every value fits in 32 bits.
* **B**: both halves used (a packed pair).
* **C**: cons-table slots, two words per slot: the value word (`B t + i + 1`) and the key word.
* **D**: memo slots, four words per slot: stamp, `k1`, `k2`, value.
* **E**: mixed records.
* **F**: unclear (mostly 32-bit values, plus `Nat` fields with no 32-bit bound in the model).
* **G**: genuinely 64-bit.

## 3. con-ron's layout for the same data

From con-ron's sources (`_tmp/ref/con-ron/crates/con-ron-core/src`):

| data | con-ron | ours |
|---|---|---|
| handle | `u32`: tag bits 31–28, tier bit 27, index 26–0 (`arena/handle.rs:66`) | the same word, stored in a 64-bit word or a packed half |
| node rows | `Tbl { rows: Vec<(A, D)> }`: the record and its derived word together; `app` row = `AppNode{f,a: u32}` + `u64` der = **16 B** (`arena/store.rs:188, 860`) | `AREC` 8 B + `ADER` 8 B = **16 B** (two arrays) |
| derived word | **`u64`**: hash32 in bits 63–32, bvar bound (15 bits), fvar range (15 bits), `lp` bit (`kernel/expr.rs:210`) | 31 bits in a 64-bit word: no hash, so the upper half is empty |
| cons slot | `HashMap2`: `Slot = Vacant \| Live(epoch: u32, K, V)`; `app` slot 20 B (tag, stamp, key 8, value 4); `clear` = `epoch += 1` (`ron/hashmap2.rs:89`) | 16 B: value word (epoch folded in: `B + i + 1`), key word; 4 per line against con-ron's 3.2 |
| table growth | a new table at twice the size; the old one is freed after the move (both live during the move) | in place (D38) |
| core caches (`whnfCore`, `infer`, …) | `HashMap2<EIdx, EIdx>`: **16 B** slots (`arena/core_state.rs:365`) | 32 B memo slots |
| per-call memos (`inst1`, `instL`, `lift`, …) | `HashMap2<EIdxNat{h: u32, d: u64}, EIdx>`: about 32 B | 32 B |
| export id tables | `IdTable { dense: Vec<u32>, sparse: HashMap }` (`frontend/scan_types.rs:538`) | dense part at 32 bits too (two per word) |
| `proj`, `bvar`, `fvar`, `Name.num` | `u64` fields | 64-bit words |
| `Nat` | `Vec<u64>` limbs | pool limbs |
| name strings | `Vec<u32>` code points, stored in the row and again in the cons key | bytes, 8 per pool word, stored once |
| input | streamed in 4 MiB chunks (`con-ron/src/driver.rs:943`) | `mmap` of the whole file, all of it resident by the end |

So con-ron uses `u32` exactly where a handle is stored (records, slot values, the dense id
table) and for its stamps. Its derived word and its scalar fields are `u64`. Where the twins
differ in bytes, we are larger in two places: the core caches' slots (32 B against 16 B) and the
empty half of `ADER` (con-ron fills it with a hash). We are smaller in the cons slots, the name
strings and the table growth. Our 32 B memo slot is a generic schema with two-word keys and a
64-bit stamp; con-ron specialises the slot by type.

## 4. Hot paths

From the profiles (`parsespeed.md` §2.2, `internspeed.md` §2, `dense.md` §1):

* **`ASLOT`**: `app_find`'s slot load is 17.7 % of the cycles of a whole run (78 % of its
  samples sit on the instruction after the load). A probe reads 3.25 slots on average. At 16 B
  there are 4 slots per line; at 12 B there would be 5.3, which saves well under one line per
  probe. The miss is one random line per lookup either way.
* **`ADER`**: `der_b` is 11.1 % of the cycles, mostly a load of a child's derived word, randomly
  into the recent past. At 32 bits, 16 words share a line instead of 8. This is the one place
  where halving could cut misses, so it was prototyped (§6).
* **`ILMEMO`**: `ilm_find` is 5.1 %, with 1.08 G base loads. Its slots would only shrink with
  mixed-width memo slots (class D).
* **`AREC`** (1.06 G variable-index checks) is a packed pair already. **`EID`** is already
  packed.
* `CTL` dominates the bounds checks and base loads (`dense.md`), but it holds 64-bit counters,
  tops and epochs: not a 32-bit candidate.

## 5. What the feature would take

**L semantics** (`L/Syntax.lean` 244 lines, `L/Semantics.lean` 394).
* A third array family: `Mem.halves : TieredArray → Array UInt32` (keyed like `words`, since
  `ADER` and the slot tables are tiered). Typing the elements `UInt32` makes every load
  `< 2^32` by type, with no invariant in specs.
* New forms: `ld32`, `st32`, `len32`, and for the tiered arrays `ld32t`, `st32t`, `len32t`.
  `copy32` is needed for the freeze (`fz_*` copies the frozen tiers into `OUT`).
* `st32` stores the low 32 bits of a `Word`, as `st8` stores the low byte. `ld32` zero-extends.
* That is 6–7 constructors. Every match over `Expr`/`Stmt` needs new cases: about 10 sites in
  the compiler, and 23–26 files that match `ld64t`/`st64t` today (`Agree`, `DefAssign`,
  `PureEval`, `WF`/`WFFast`, `Checker/Prelude*`, `Rom/*`, E2E serialisation and trace,
  `ConsLib*`, `FreezeSpec`).
* The array table (`L/Arrays.lean`, `ArrKind`) gets a third kind, `half` (or `word32`), and
  `Prog.wf` checks the kind per access, as it does for bytes (`absarrays.md` §8.3).

**Compiler** (`Compiler/Compile.lean`, 2 004 lines).
* `genLd`/`ldA`/`mbx` carry a `Bool byte` flag today, which becomes a three-way width: scale 4
  and a `movl` into the 32-bit register. Kraken's x64 semantics already zero-extends on a
  `.W32` register write (`X64/Semantics.lean:103`), and `MachineData.load`/`store` are generic
  over `Width`. Kraken therefore needs no change; ConAgua's compiler uses no `W32` yet.
* `Compiler/Mem.lean` (146 lines, 8-byte `rdW`/`wrW` and 1-byte `get?` only) needs `rd32`/`wr32`
  and analogues of `rdW_wrW_same`, `rdW_wrW_A` and `get?_wrW_A`.
* `MemRel` (`Rel.lean`) gets `size32`/`get32`, and `Layout.Ok` gets one more disjointness
  family, or a width per position if the families merge into one array space (`dense.md` §2).
* The simulation lemmas are a third copy of the byte path (`MemRel.store8` … `sim_st8`, about
  200 lines in `SimStore.lean`), plus the loads in `SimExpr.lean`. Constant indices fold `4 k`
  into the displacement, and minimum lengths (`min k`) carry over.
* Second code generator: `scripts/leafgen/LGEmit.lean` (833 lines) matches every array form.
  The model generator `L/ModelGen.lean` and the notation (`.u64`/`.u8` → `.u32`) need cases too.

**Entry stubs and `Final`.**
* A 32-bit array's slot holds `2^33` elements, so capacities change, and `cap_check` reads its
  length in elements.
* The freeze/`OUT` image and `ca_check_b`'s length tests need a width per frozen array.
* `loadMem`/`seqMem0`/`bufMem0` get the third family.
* `checkerFile_eq` is regenerated.

**Per-function proofs, for each migrated array.** `ADER` appears in 31 files (105 lines). Its
reads `rdW (m.arr64 ADER) i` become `rd32 (m.halves ADER) i`. The derived-word relations
(`DerR`, `packBFL`) lose their `< 2^31` side conditions where the type gives them. Frames
between families are free (separate fields of `Mem`), as between `bytes` and `words` today.

**Estimate.** Semantics, compiler, simulation and stubs come to 1 500–2 500 lines touched. That
is the size of the absarrays switch (1 000–1 300 lines) plus a new family's lemmas: about 40–80
agent-hours. Migrating the `ADER` family (five derived-word arrays, both tiers) adds 300–500
lines, 10–15 agent-hours. Mixed-width records (classes C and D) are a separate and larger
design. They would need a record notion with per-field widths and a slot stride in bytes,
touching `TRec`, `ConsLib`, `MemoLib` and their specs (`ConsLibSpec`, `MemoLib` specs). That
is not estimated here.

**Alternative: hand-packing in L** (no compiler change). The id tables already do it.
`Front/IdTable.lean` stores entry `i` in half `i & 1` of word `i >> 1` (`dnW`, `dnSet`; a
store is a read-modify-write), and its relation `TblR` carries the `< 2^32` bound. A
generalised **half-word column** (a `TRec` variant: field `i` at word `i >> 1`, half `i & 1`)
would cover the `ADER` family at the same per-array cost as the feature's migration (300–500
lines). The price is 2–3 instructions per load and a read-modify-write per store. The writes to
a frozen tier never happen, and each worker owns its tier 1, so the read-modify-write is safe
in the parallel mode. This reaches class A only, the same 29 MB as the feature.

## 6. Prototype: `ADER` at 32 bits (unproved)

`checker_ader.s` is `checker.s` with the four `ADER` accesses rewritten: the two loads in
`der_b` and `fvar_push`'s read of the type's `lp` bit (`movq (b,i,8)` → `movl (b,i,4)`), and the two stores in
`mk_app` (`movq` → `movl`, scale 4). The bounds checks still compare with the length in words,
which is generous and harmless for a prototype. The freeze copy (`fz_40`) is not adapted, so
the prototype is valid on one thread only.

* **Verdicts:** `diff-e2e --bin ader_clean --parallel 8`: every fixture agrees (0
  UNSOUND/INCOMPLETE/CRASH/TIMEOUT).
* **Memory** (`Init`, THP off): `ADER⟨0⟩` 41.68 → 20.84 MB, `ADER⟨1⟩` 3.14 → 1.57 MB,
  `ru_maxrss` 748.0 → 725.8 MB (−22.1 MB, −3.0 %).
* **Wall** (`Init`, one thread, interleaved paired rounds, `taskset -c 44,92`, `wb.py`/`wstats.py`
  of `_tmp/internspeed/`). There were 30 rounds in two batches, at load 4–68 (median 19). The
  base median is 21.5 s, against 18.2–18.8 s on a quiet machine:

  | | n | median paired | Wilcoxon p | mean, 95 % CI |
  |---|---:|---:|---:|---:|
  | batch 1 | 16 | −2.7 % | 0.009 | −7.0 % [−15.2, +1.9] |
  | batch 2 | 14 | −1.6 % | 0.153 | −7.7 % [−19.1, +5.3] |
  | **both** | 30 | **−2.1 %** | **0.003** | −7.4 % [−13.9, −0.3] |

  The result is a likely gain of about 2 %, measured under load. Load inflates memory-bound
  effects, and `dense.md` and `internspeed.md` both saw gains shrink on a quiet machine. A quiet
  rerun should confirm it before anyone builds on it. The instruction count is unchanged: the
  same instructions, with `movl` and scale 4.

**Rerun** (lane hpmeasure): the same four edits on master 7904aa4e's `checker.s` (after
`presize`/`rnat`), 40 interleaved rounds per cell, `_tmp/hpmeasure/`:

| cell | base | median paired | Wilcoxon p | load |
|---|---:|---:|---:|---|
| parse phase (46/94) | 1.90 s | **−0.5 %** | < 0.001 | 4–13 |
| one thread (44/92), all 40 rounds | 18.87 s | −1.2 % | 0.785 | 3–127 (median 14) |
| ↳ the 20 rounds at load < 20 | | **−1.6 %** | 0.004 | |

`ru_maxrss` 743.8 → 720.8 MB (one thread), 645.7 → 625.2 MB (parse); cycles −1.7 % (one run).
The gain holds at about 1.5 %, smaller than the first 2.1 %; the load filter is post hoc.

An `EID` variant (the same rewrite of `expr_get`/`expr_put`) is rejected on `Init`. `EID`
already holds two entries per word, so a 32-bit scale breaks its packing. That is how this
survey found the existing hand-packing.

## 7. Recommendation

1. **Do not design 32-bit arrays in L now.** A per-array width reaches 29 MB on `Init` (3.9 % of
   RSS) for 40–80 agent-hours of compiler and stub work. Everything beyond that needs
   mixed-width records, a larger design.
2. **The RSS gap is the input.** 346 MB of the 748 MB is the `mmap`ed export; con-ron streams.
   Any lane that targets peak RSS should start there, in `main.c` and the input ABI, not in L's
   array widths. Possible routes: unmap or `MADV_DONTNEED` the consumed prefix; on the
   sequential path, the phase split `run_jobs` already uses, which unmaps the input after
   phase A. Both need their own measurement; this survey made neither.
3. **`ADER` is the one candidate.** The prototype measured −2.1 % wall time (p = 0.003, under
   load) and −22 MB. If a quiet rerun confirms the gain, pack the derived words two per word
   in L, as the id tables do. The packed load costs 2–3 more instructions than the
   prototype's `movl`, so measure that version again before landing it. A shared half-word-column library, used by
   `ADER`/`LADER`/`FADER`/`LEDER`/`PJDER`, would cost about 300–500 lines and save 26 MB.
   Otherwise leave it.
4. **The core caches' slots** (32 B against con-ron's 16 B for `EIdx → EIdx`) are the
   memo-layout question, not a width feature. If the memos are ever re-laid out, a one-word-key
   schema with packed `k1 | v << 32` (stamp in its own word) would halve them in plain L.
